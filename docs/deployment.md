# 低显存 LLM 推理部署与性能实验

本文整理单机部署配置与历史实验结果，作为[项目首页](../README.md)的技术补充。数据来自既有实验记录，本次文档整理未重新运行模型。

## 环境与目标

| 项目 | 实验环境 |
| --- | --- |
| CPU | Intel Core i7-8750H，6 核 12 线程 |
| GPU | NVIDIA GTX 1060 Max-Q，6GB 显存，Compute Capability 6.1 |
| 系统内存 | 32GB DDR4-2666，双通道 |
| 推理节点 | Windows，CUDA 运行环境 |
| 模型 | Ornith-1.0-35B，MoE，约 35B 总参数 / 3B 激活参数 |
| 权重格式 | GGUF，Q4_K_M，文件约 19.71GB |
| 已验证运行时 | llama.cpp b8600；参数与兼容性结论针对该历史部署组合 |
| 对外接口 | OpenAI 兼容 `/v1/chat/completions` |

目标是在现有硬件资源内运行模型，为上层应用提供可调用的推理端点。模型并未全部驻留在 6GB 显存中：MoE 专家层主要使用 CPU 和系统内存，非专家层及量化 KV Cache 使用 GPU。

## 资源配置策略

| 约束 | 配置选择 | 验证方式 |
| --- | --- | --- |
| 模型权重大于显存 | 专家层保留在 CPU，其余可卸载层使用 GPU | 查看层分配、后端 buffer 与设备日志 |
| 长上下文 KV Cache 占用显存 | 使用 q8_0 KV Cache 量化并放在 GPU | 检查实际上下文容量与 KV buffer 分配 |
| 模型权重需要从系统内存读取 | 使用 `--no-mmap` 配置预载，关注内存余量 | 观察加载结果、内存及生成 timing |
| 注意力计算的显存开销 | 显式启用 Flash Attention | 对比运行日志与计算 buffer 分配 |
| 参数可能被运行时自动调整 | 显式设置上下文并关闭该版本的自动 fit | 以启动日志中的实际容量为准 |

这些策略使用推理引擎已有能力，部署工作重点是理解资源开销、选择配置并验证实际执行情况。

## 已验证启动配置

以下为 llama.cpp b8600 的历史配置示例。不同版本的命令行参数和模型支持情况可能不同，迁移前应检查对应版本的帮助信息与启动日志。

```bash
llama-server -m ornith-1.0-35b-Q4_K_M.gguf \
  -ngl 999 -cmoe --no-mmap \
  -c 196608 -kvo -ctk q8_0 -ctv q8_0 \
  -fa on -fit off --jinja --host 0.0.0.0 --port 8080
```

| 参数 | 在本次部署中的用途 |
| --- | --- |
| `-ngl 999` | 请求卸载可用层；与 `-cmoe` 配合，实际放置以日志为准 |
| `-cmoe` | 将 MoE 专家层保留在 CPU |
| `--no-mmap` | 禁用内存映射，采用预载配置 |
| `-c 196608` | 请求配置 192K 上下文容量 |
| `-kvo -ctk q8_0 -ctv q8_0` | KV Cache 放在 GPU，Key / Value 使用 q8_0 量化 |
| `-fa on` | 显式启用 Flash Attention；所测版本的 Value Cache 量化依赖此项 |
| `-fit off` | 防止所测版本自动缩减请求的上下文容量 |
| `--jinja` | 启用模型聊天模板 |

`--host 0.0.0.0` 用于跨主机接入，应结合部署环境设置访问控制。

## 性能结果与解释

| 实验配置 | 历史结果 | 说明 |
| --- | --- | --- |
| 纯 CPU，b10301 | 约 10.3 token/s | 当时所测模型未成功卸载到 GPU |
| b8600，CPU/GPU 混合执行 | 17.76 token/s | 同时改变运行时版本和卸载情况，不是隔离单变量的 GPU 加速比 |
| b8600，192K 配置及量化 GPU KV Cache | 18.03 token/s | 短提示请求的生成阶段测速 |
| CPU 线程数与内存锁定对照 | 约 17.6–17.9 token/s | 未观察到稳定的额外收益 |

历史记录中，192K 配置的 GPU KV Cache 约 2.04GB，总显存占用约 4.5–4.9GB，系统内存余量约 7GB。不同采样时刻和配置的占用有所差异，这些数值用于描述资源预算。

**容量与吞吐分开解释：** 配置 192K 上下文，表示运行时分配了相应容量；约 18 token/s 来自短提示实验。现有记录不能据此证明满 192K 输入时的吞吐、长上下文质量或多请求服务能力。

**区分 prefill 与 decode：** 电源计划调整曾改善提示处理速度，但生成阶段没有相同比例的收益。模型加载成功、HTTP 健康检查通过和端到端推理成功，也应分别验证。

历史调优将系统内存带宽视为生成阶段的重要限制。这里将其作为结合硬件与实验的瓶颈判断，不把理论带宽估算表述为已经证明的“物理极限”。

## 兼容性排查与方案取舍

### GPU 可识别，但模型仍在 CPU 执行

当时所测 b10301 与 GGUF 组合出现层分配到 CPU 的情况；切换到 b8600 后实现 GPU 卸载。排查同时检查 CUDA 设备列表、运行库、模型元信息和层分配日志，而非仅凭 GPU 是否存在判断卸载成功。

此结果只说明历史模型文件与运行时组合的兼容性，不能推广为当前 llama.cpp 主线始终不支持该模型。

### KV Cache 放置影响生成速度

历史实验中，将 KV Cache 放回 CPU 的配置测得约 11.25 token/s，低于量化 GPU KV Cache 方案。部署配置因此保留 GPU KV Cache，并结合显存预算控制上下文容量。

### Flash Attention 的价值需要分别测量

固定为 f16 KV Cache、128K 配置后，Flash Attention 开关的历史生成速度对照约为 17.36 与 17.68 token/s，差异较小；计算 buffer 分配则由约 4581MB 降至约 871MB。该实验支持其显存配置价值，不能把 buffer 减少直接当作等比例的吞吐提升。

### 投机解码受版本与模型支持限制

在所测 b8600 与 qwen35moe 模型组合中，draft 模型能够加载，但运行时报告 `speculative decoding not supported by this context`，未获得生成加速。该结论限于此次组合，不代表其他模型或新版运行时的能力。

## 自动化与诊断入口

- [远程启动](../scripts/start_ornith.py)：通过 SSH 写入启动配置、处理旧进程、设置优先级、轮询加载日志并请求 `/health`。
- [测速与资源采样](../scripts/quick_speed.py)：发送样例请求后读取运行日志中的 timing，并查询 GPU 显存和系统内存。
- [环境诊断](../scripts/diag_perf.py)：检查电源计划、内存频率与进程信息。
- [Web 服务接入](../claude-web/README.md)：连接推理端点、协议转换服务与流式 Web 客户端。

公开脚本中的连接信息为占位符，需要按自己的环境配置。启动脚本会停止目标推理进程，执行前应确认目标主机和路径。测速脚本通过日志读取最近 timing，主要服务于人工诊断；它没有为每个请求生成可关联的独立实验结果，尚不是完整基准测试框架。

## 验证流程

1. 检查 CUDA 设备识别、模型文件与运行库。
2. 启动服务，核对日志中的层分配、实际上下文容量和 buffer 大小。
3. 请求 `/health`，确认加载就绪。
4. 发送推理请求，确认接口响应和正文输出。
5. 读取 prefill / decode timing、显存与系统内存，结合固定条件进行重复实验。

后续基准测试应固定输入与输出长度、采样参数、预热及重复次数，并补充 TTFT、并发行为和长时间运行结果。
