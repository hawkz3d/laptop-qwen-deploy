**✅ 2026-08-08 突破（GPU offload 解法）：** 用**老版 llama.cpp b8600**（2026-02，fused 要求引入前）能正常 offload qwen35moe！部署到 `<LLAMA_OLD_DIR>\bin`（从 <LLAMA_DIR> 复制 cudart/cublas dll 后 CUDA 正常识别 GTX1060）。

**🏆 最终最优配置（2026-08-08 定稿）：** `llama-server -m <MODELS_DIR>\ornith-1.0-35b-Q4_K_M.gguf -ngl 999 -cmoe --no-mmap -c 196608 -kvo -ctk q8_0 -ctv q8_0 -fit off --jinja --host 0.0.0.0 --port 8080` → **实测 18.03 t/s，192K 上下文，显存 4.5GB（75%），内存余 7.4GB**。要点：`-cmoe` 专家留 CPU（6GB 显存放不下 15GB 专家，硬上限）；**`-fit off` 必须**（否则 fit 把 `-c` 静默降到 131072）；KV 必须 `-ctk q8_0 -ctv q8_0` 量化放 GPU（192K KV 2.04GB），`--no-kv-offload` 不可取（11.25 t/s 大降）。`-ncmoe`/`-ot` 部分专家 GPU 不可行（15GB pinned 卡死 / override 无效）；ngram 投机不支持（GDN 架构 partial sequence removal）。一键启动：`<SCRIPT_DIR>\start_ornith.py`（已固化 192K 配置）。**视频 17 t/s 真相：老版 llama.cpp（+TurboQuant fork）能 offload qwen35moe；ik_llama.cpp 需 Ampere+。**

**2026-08-08 二次定稿（18 t/s = Q4 带宽物理极限，用户决策收工）：**
- **带宽账本确认极限**：Q4 每 token 从 DDR4 读 ~1.69GB（3B 激活 × 0.563B），18 t/s = 30.4 GB/s，已达 DDR4-2666 双通道实际上限（~30-32GB/s）的 90%+。**17-18 t/s 就是这台机器 Q4 的物理天花板**。
- 排除项：杀多余进程速度不变（进程竞争排除）；High Performance 电源计划已切（prefill 9.67→28.33 生效，但 eval 不变，因为 eval 是带宽瓶颈）。
- **Turbo Boost 被 BIOS 禁用**：`MaxClockSpeed` 锁 2208，满载采样全程 2208；`powercfg /setacvalueindex ... 3b04d4fd... 2`（Aggressive）无效 → 必须进 BIOS（F2）开 Intel Turbo Boost，预期 <1 t/s（带宽已饱和）。
- **进程优先级 High = +9%（16.5→18.0 t/s）**：`start_ornith.py` 已固化启动后 `$p.PriorityClass='High'`；bat 保持前台原样。
- **到 21+ 唯一路径 = 换小量化**：Q3_K_M(~16.5GB)→~20-21 t/s；IQ3_XXS(13GB)→~24-25 t/s（还能省 6-7GB 内存给 KV）。用户决策：**停在 Q4 18 t/s，不换模型**。
- 当前运行态：192K ctx / 18 t/s / VRAM 4.5GB / 内存余 7.4GB / High 优先级 / High Performance 电源计划。

**2026-08-14 Flash Attention 实测结论：**
- `-fa off` 启动失败：`V cache quantization requires flash_attn` —— V cache 量化（`-ctv q8_0`）强制依赖 Flash Attention。
- `auto` 自动判定为 enabled（日志 `Flash Attention was auto, set to enabled`），此前 18 t/s 均在 FA 开启下测得。
- `-fa on` 与 `auto` 等价（都 enabled），实测 eval 17.49 t/s；不影响 18 t/s 的 DDR4 带宽天花板（eval 瓶颈是权重读取带宽，非注意力计算）。
- 启动命令已显式加入 `-fa on`，让配置不依赖 auto 的隐性行为。


**2026-08-14 上 20 t/s 探索定论（FA 对照 / 线程 / mlock / 投机解码）：**

**FA on vs off 严格对照**（KV 均 f16 不量化、128K，隔离 FA 变量，各 3 次）：
- FA-OFF eval **17.36** t/s（17.50/17.35/17.24）vs FA-ON **17.68** t/s（18.07/17.44/17.53）→ FA 只快 +1.8%，噪声内，**FA 不构成 eval 瓶颈**（带宽饱和）
- FA 真正价值 = **显存**：`sched_reserve CUDA0 compute buffer` FA-OFF **4581MB → FA-ON 871MB**（省 3.7GB）。这就是 `-ctv q8_0` 硬依赖 FA 的根因——只有 FA 开时 compute buffer 才小到塞下 192K KV 量化 + 模型

**线程 / --mlock**（192K，各 3 次）：`-t 12 -tb 12`=17.70、`--mlock`=17.60、`-t 12 --mlock`=17.89、基线=17.75 → 全部噪声内，**无效**。默认 n_threads=6（物理核），显式 12 线程也不加速

**投机解码（结论：架构不可行）：**
- b8600 有全套 draft 参数（`-md/--model-draft`、`--draft-max`、`-ngld`、`-ctkd/-ctvd`）但**无 `--mtp`**；Ornith 有 MTP 变体 GGUF（wang-yang/SC117）但 b8600 用不了
- 唯一同词表小模型 = `Ornith-1.0-9b-Q4_K_M.gguf`（5.24GB）；实测 `-md` 9B draft：draft 能加载但日志铁证 **`speculative decoding not supported by this context`**（qwen35moe 不支持 partial sequence removal），eval=17.62 无提升，draft 白占 4.8GB 内存
- **MTP / LLM draft / ngram 三条路全被 qwen35moe 架构堵死**

**Q6_K_M 带宽账本**：Q4 每 token 读 1.69GB（3B 激活）→18 t/s=30.4GB/s（DDR4-2666 双通道 90%+）；Q6 每 token 2.27GB → 预计 **13.4 t/s**，达不到 18；压缩 ctx 到 128K 无帮助（eval 与 ctx 无关，KV 在 GPU）

**定论：** 18 t/s 是 GTX1060 + DDR4-2666 的软件层天花板。突破 20 只剩①换更小量化（Q3_K_M~20-21 / IQ3_XXS~24-25，用户排除）②换硬件（更大显存 GPU 把专家放进显存，绕开 CPU 带宽）
